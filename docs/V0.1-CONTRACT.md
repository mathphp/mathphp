# v0.1 scalar-expression contract

Status: **Normative implemented specification; public identity resolved**

This document defines the complete v0.1 behavior implemented by MathPHP. On
2026-07-30, the user explicitly retained the `MathPHP` product name,
`mathphp/mathphp` Composer coordinate, and `MathPHP\` namespace while accepting
the collision risk recorded in `docs/IDENTITY-GATE.md`.

The words **must**, **must not**, **should**, and **may** are normative.
Requirement IDs are stable traceability labels for implementation, tests, and
release review.

## 1. Scope

`LANG-001` v0.1 evaluates one scalar expression to one finite PHP `int` or
`float`.

`LANG-002` The language includes:

- integer, decimal, and scientific-notation literals;
- variables;
- the constants `pi` and `e`;
- grouping parentheses;
- binary `+`, `-`, `*`, `/`, `%`, and `^`;
- unary `+` and `-`;
- at most one postfix factorial per postfix expression; and
- calls to explicitly registered functions.

`LANG-003` The language is ASCII and case-sensitive. Source locations are byte
locations rather than Unicode character locations.

`DEF-001` v0.1 does not include implicit multiplication, assignments,
comparisons, logical operators, strings, arrays, symbolic algebra,
simplification, derivatives, equations, units, currency, matrices, complex
numbers, formatting, comments, or arbitrary precision.

## 2. Lexical contract

### 2.1 Whitespace and identifiers

`LEX-001` The ASCII bytes space, tab, line feed, carriage return, form feed, and
vertical tab are insignificant between tokens. Whitespace inside a token is not
permitted.

`LEX-002` An identifier matches:

```regex
[A-Za-z_][A-Za-z0-9_]*
```

Identifiers and function names are case-sensitive. Unicode letters and all
other non-ASCII bytes are rejected.

### 2.2 Numeric literals

`LEX-003` A number matches:

```regex
(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?
```

Valid examples include:

```text
0
007
42
1.
.5
0.125
1e3
1E-3
.5e+2
1.e2
```

`LEX-004` A literal containing neither `.` nor an exponent is an integer
literal. It must fit within the host's `PHP_INT_MAX`; otherwise it is a lexical
range error. Its sign is never part of the literal.

`LEX-005` A literal containing `.` or an exponent is a float literal. Conversion
must produce a finite PHP float. Float overflow, hex, binary, and octal prefixes
are not valid number syntax. Alphabetic spellings such as `NaN`, `INF`, and
`Infinity` lex as ordinary case-sensitive identifiers; they are not special
numeric literals, and host-supplied values must still satisfy `ENV-003`.

`LEX-006` Malformed numeric continuations are lexical errors rather than
multiple valid tokens. Once `e` or `E` follows a mantissa, the lexer commits to
an exponent and requires optional sign followed by at least one digit. A `.`,
`_`, `e`, or `E` immediately following a completed number is a malformed
numeric continuation. Other identifier starts remain separate tokens so `2pi`
is rejected by full-input parsing rather than treated as a number.

Malformed-number spans begin at the number's first byte and include the
contiguous malformed numeric run:

| Source | Error span |
|---|---|
| `1e` | `[0,2)` |
| `1e+` | `[0,3)` |
| `1efoo` | `[0,5)` |
| `1e_2` | `[0,4)` |
| `1e2.3` | `[0,5)` |
| `1.e` | `[0,3)` |
| `1..2` | `[0,4)` |
| `1.2.3` | `[0,5)` |
| `1e2e3` | `[0,5)` |
| `1e2e+3` | `[0,6)` |
| `1e2e-3` | `[0,6)` |
| `1_000` | `[0,5)` |

For this purpose, a malformed numeric run continues through adjacent ASCII
letters, digits, underscores, and decimal points, plus a sign immediately
following an exponent marker. It ends before whitespace, a delimiter, or any
other operator.

### 2.3 Tokens and complete input

`LEX-007` Token types are number, identifier, each individual operator or
delimiter (`+ - * / % ^ ! ( ) ,`), and EOF. Every token includes its lexeme and
source span.

`LEX-008` Any source byte that cannot begin a valid token produces a lexical
exception at that byte. The lexer never silently skips unknown input.

`LEX-009` The lexer always emits one EOF token whose span is
`[sourceLength, sourceLength)`.

## 3. Grammar and precedence

`SYN-001` The normative grammar is:

```ebnf
input          ::= additive EOF
additive       ::= multiplicative (("+" | "-") multiplicative)*
multiplicative ::= prefix (("*" | "/" | "%") prefix)*
prefix         ::= ("+" | "-") prefix | power
power          ::= postfix ("^" prefix)?
postfix        ::= primary ["!"]
primary        ::= NUMBER
                 | IDENTIFIER
                 | IDENTIFIER "(" [arguments] ")"
                 | "(" additive ")"
arguments      ::= additive ("," additive)*
```

An identifier followed by `(` after token-level whitespace is a function call.
Otherwise it is a constant or variable reference.

`SYN-002` From highest to lowest, precedence is postfix factorial,
exponentiation, unary sign, multiplicative operators, then additive operators.
Exponentiation is right-associative. All other binary operators are
left-associative.

Required outcomes are:

| Expression | Meaning | Result |
|---|---|---:|
| `2^3^2` | `2^(3^2)` | `512` |
| `-2^2` | `-(2^2)` | `-4` |
| `2^-2` | `2^(-2)` | `0.25` |
| `(-2)^2` | grouped negative base | `4` |
| `-3!` | `-(3!)` | `-6` |
| `(-3)!` | factorial of a negative value | evaluation error |

`SYN-003` Repeated postfix factorial such as `3!!` is not valid v0.1 syntax.
Nested factorial remains expressible with explicit grouping, subject to all
normal limits.

`SYN-004` Parsing must consume EOF. Adjacent primaries such as `2pi`, `2(3)`,
and `(2)(3)` are parse errors; they are not implicit multiplication.

`SYN-005` Empty input, missing operands, unmatched delimiters, empty argument
slots, trailing commas, stray commas, and trailing tokens are parse errors with
the most specific available span.

## 4. Values, variables, and constants

`ENV-001` The only expression values and public results are PHP `int` and
`float`. Booleans, numeric strings, arrays, objects, resources, and `null` are
never coerced.

`ENV-002` The constants are exactly lowercase `pi` and `e`, using the host PHP
runtime's finite double-precision values for π and Euler's number. They are
reserved and cannot be overridden by variables.

`ENV-003` Variables are supplied by the host as a string-keyed map. Names must
match `LEX-002`, must not be reserved constants, and values must be finite
`int|float`. Invalid host-supplied maps produce `InvalidArgumentException`.
An identifier that is valid syntax but absent from the environment produces an
evaluation exception at that identifier.

`ENV-004` Every evaluation receives a newly constructed environment containing
a defensive copy of its variable map and an immutable function registry. No
mutable static or global environment, evaluator, variable map, function map, or
options object is permitted. An immutable registry object may be safely shared;
its membership cannot be changed after construction.

`ENV-005` Sequential, nested, and concurrent evaluations must not observe
variables or registry membership supplied to another evaluation. A default
registry may share immutable definitions but no call-specific mutable state.
PHP closures can capture external mutable objects or references; that
host-controlled state is outside the library's isolation guarantee and is why
custom callbacks are required to be trusted and pure under `FUN-003`.

## 5. Numeric contract

### 5.1 General rules

`NUM-001` Integer literals produce `int`; decimal and scientific literals
produce `float`. Operators preserve the rules below rather than normalizing
integral floats into integers.

`NUM-002` A public result and every stored intermediate must be finite. An
operation or function that produces `NaN`, positive infinity, or negative
infinity produces an evaluation exception. Float underflow to zero is allowed.
Negative zero is normalized to positive `0.0`.

`NUM-003` Integer overflow is an evaluation error. Exact integer operations
must not silently promote to float and lose precision. Arbitrary precision is
outside scope; users may write an explicit decimal or scientific literal when
they intentionally want floating-point arithmetic.

### 5.2 Unary and ordinary arithmetic

`NUM-004` Unary `+` preserves the operand type and value. Unary `-` preserves
the operand type except that negating `PHP_INT_MIN` is integer overflow.

`NUM-005` For `+`, `-`, and `*`:

- two integer operands produce an integer if the exact result fits the host
  integer range, otherwise integer overflow;
- if either operand is float, the operation produces a finite float.

`NUM-006` `/` always produces a float. Divisors `0` and both signed forms of
`0.0` produce a division-by-zero evaluation exception.

`NUM-007` `%` is truncated-toward-zero remainder with the sign of the dividend,
matching PHP integer remainder semantics. Both operands must be exactly
integer-valued and within the host integer range. Integral floats such as
`5.0` are accepted; fractional values are domain errors. A zero divisor is a
modulo-by-zero evaluation exception. `PHP_INT_MIN % -1` is defined as `0` and
must be handled without relying on a host operation that may throw. The result
is an integer.

Integer-valued checks are exact: an `int` qualifies; a float qualifies only if
`floor(value) === value` and it is in the platform-safe half-open interval:

```text
[-2^(PHP_INT_SIZE*8 - 1), 2^(PHP_INT_SIZE*8 - 1))
```

The power-of-two bounds are exactly representable as floats. The upper bound is
exclusive because converting `(float) PHP_INT_MAX` is not safe on 64-bit PHP:
it rounds to `2^63`. Tolerances are not used for domain decisions.

### 5.3 Exponentiation

`NUM-008` `^` implements real-number exponentiation under these rules:

- its right operand's absolute value must not exceed the configured exponent
  limit;
- zero raised to a negative exponent is a division-by-zero error;
- zero raised to zero has mathematical value one;
- a negative base requires an exactly integer-valued exponent;
- negative exponents and valid fractional powers produce float;
- if both operands are integers and the exponent is non-negative, the result is
  integer only when exactly representable, otherwise integer overflow;
- if either operand is float, the result is float; and
- every result must satisfy `NUM-002`.

The exponent limit is checked before exponentiation. No tolerance is used to
decide whether an exponent is integral.

### 5.4 Factorial

`NUM-009` Factorial accepts an exactly integer-valued operand from zero through
the configured inclusive limit. It is computed iteratively and exactly as an
integer; `0!` and `1!` are `1`.

The numeric hard maximum is the greatest `n <= 20` for which `n!` fits
`PHP_INT_MAX`: normally 20 on 64-bit PHP and 12 on 32-bit PHP. The configured
limit may be lower but never higher. Negative, fractional, out-of-range, and
non-finite operands are evaluation errors.

### 5.5 Floating-point conformance

`NUM-010` Finite floating-point behavior otherwise follows the host's IEEE-754
double precision and mathematical library. The language has no comparison
operator. Conformance tests and documentation compare expected finite floats
using:

```text
abs(actual - expected)
<= max(1e-12, 1e-12 * max(abs(actual), abs(expected)))
```

Integers and result types are compared exactly.

## 6. Function registry

`FUN-001` An expression can invoke only a function definition present in the
evaluation's explicit registry. The implementation must never call a PHP
function merely because its name matches an expression identifier. `eval`,
string-to-callable lookup, variable functions derived from source text, and
unrestricted `call_user_func` dispatch are forbidden.

`FUN-002` The immutable default registry contains this complete allowlist:

| Function | Arity | Domain and result |
|---|---:|---|
| `abs(x)` | 1 | finite; preserves type; `abs(PHP_INT_MIN)` overflows |
| `sqrt(x)` | 1 | `x >= 0`; float |
| `sin(x)` | 1 | finite input and output; float |
| `cos(x)` | 1 | finite input and output; float |
| `exp(x)` | 1 | finite output; float overflow is an error |
| `ln(x)` | 1 | `x > 0`; float |
| `log(x, base)` | 2 | `x > 0`, `base > 0`, `base != 1`; float |
| `floor(x)` | 1 | finite; float |
| `ceil(x)` | 1 | finite; float |
| `round(x)` | 1 | finite; float; halfway cases round away from zero |

Names are lowercase and case-sensitive. Wrong arity, unknown functions, and
domain violations are evaluation exceptions at the complete call span.

`FUN-003` Host applications may add explicitly constructed trusted custom
function definitions. Each definition has a validated identifier, fixed
minimum and maximum arity, and a `Closure`; it must declare itself pure and
side-effect-free. Built-ins and constants cannot be overridden.

Custom callbacks receive only a list of evaluated finite numeric arguments and
must return finite `int|float`. Invalid returns or thrown callback errors are
wrapped as evaluation exceptions at the call span. Definitions and registries
are immutable and scoped to one evaluation options object. The library cannot
make untrusted host callbacks safe; only expression text is treated as
untrusted input.

## 7. Errors and source spans

`ERR-001` All expression-originated failures extend one source-aware base
exception and one of three phase-specific types:

- lexical exception: malformed or out-of-range literal, unknown byte,
  expression-length limit, or token-count limit;
- parse exception: malformed grammar, trailing input, nesting limit, AST-depth
  limit, or argument-count limit;
- evaluation exception: unknown name/function, arity/domain failure, zero
  divisor, numeric overflow/non-finite result, exponent/factorial limit, or
  custom-function failure.

Invalid host API construction, such as malformed variable maps, function
definitions, or limit values, uses `InvalidArgumentException` because it has no
expression source location.

`ERR-002` Every token and immutable AST node carries a zero-based,
end-exclusive byte span `[start,end)`. Composite nodes cover their complete
source construct. Every expression exception exposes the offending span,
includes its start position in the human-readable message, and exposes a
stable machine-readable error code.

`ERR-003` EOF failures use `[sourceLength,sourceLength)`. Unknown bytes use the
one-byte span containing the offending byte. Limit failures point at the
construct that first exceeds the inclusive limit.

`ERR-004` The complete stable error-code catalog is:

| Phase | Code | Span |
|---|---|---|
| lexical | `lex.malformed_number` | complete malformed numeric run from `LEX-006` |
| lexical | `lex.number_out_of_range` | complete numeric literal |
| lexical | `lex.unknown_character` | offending one-byte source span |
| parse | `parse.empty_expression` | EOF |
| parse | `parse.expected_expression` | unexpected token or EOF |
| parse | `parse.expected_token` | unexpected token or EOF where a delimiter was required |
| parse | `parse.trailing_input` | first unconsumed token |
| evaluation | `eval.unknown_variable` | identifier |
| evaluation | `eval.unknown_function` | function-name identifier |
| evaluation | `eval.arity` | complete function call |
| evaluation | `eval.domain` | operator token, factorial token, or complete function call |
| evaluation | `eval.division_by_zero` | `/` token |
| evaluation | `eval.modulo_by_zero` | `%` token |
| evaluation | `eval.integer_overflow` | responsible operator or complete function call |
| evaluation | `eval.non_finite` | responsible operator or complete function call |
| evaluation | `eval.custom_function` | complete custom-function call |
| limit | `limit.expression_length` | first excess byte |
| limit | `limit.token_count` | first excess token |
| limit | `limit.nesting` | excess opening delimiter |
| limit | `limit.ast_depth` | operator or opening delimiter that would exceed depth |
| limit | `limit.function_arguments` | first excess argument |
| limit | `limit.factorial` | `!` token |
| limit | `limit.exponent` | `^` token |

Limit codes are raised through the phase-specific exception appropriate to the
table in section 8; there is no fourth expression-exception phase.

`ERR-005` Evaluation is deterministic and left-to-right:

- a unary or factorial operand is evaluated before its operation;
- a binary left operand is evaluated before its right operand;
- a function definition is resolved and its arity checked before any argument;
- function arguments are then evaluated from left to right before invocation.

The first failure in that order is reported. Host options, variable maps, and
function definitions are validated before expression processing. Expression
length is checked before tokenization; lexing and parsing then proceed from
left to right; evaluation begins only after a complete valid AST exists.

## 8. Resource safeguards

All configured limits are inclusive: an input exactly at a limit may succeed,
and the first value over it must fail before the expensive allocation,
recursion, or computation.

| ID | Default | Definition | Failure phase/code |
|---|---:|---|---|
| `SEC-001` | 4,096 | expression bytes, including whitespace | lexical / `limit.expression_length` |
| `SEC-002` | 1,024 | non-EOF tokens | lexical / `limit.token_count` |
| `SEC-003` | 64 | simultaneously open grouping/call parentheses | parse / `limit.nesting` |
| `SEC-004` | 128 | AST depth, with a leaf at depth 1 | parse / `limit.ast_depth` |
| `SEC-005` | 16 | arguments in one function call | parse / `limit.function_arguments` |
| `SEC-006` | platform factorial maximum | factorial operand | evaluation / `limit.factorial` |
| `SEC-007` | 1,024 | absolute exponent value | evaluation / `limit.exponent` |

`SEC-008` Limits live in an immutable per-evaluation options object. They may be
deliberately raised or lowered by trusted host code within these constructor
ranges:

| Limit | Valid configured range |
|---|---|
| expression bytes | integer `>= 1` |
| non-EOF tokens | integer `>= 1` |
| nesting | integer `>= 0` |
| AST depth | integer `>= 1` |
| function arguments | integer `>= 0` |
| factorial operand | integer from `0` through the platform maximum in `NUM-009` |
| absolute exponent | finite number `>= 0` |

A zero nesting limit forbids grouping and calls. A zero argument limit permits
only zero-argument custom calls. Zero factorial and exponent limits permit only
operand/exponent zero. Invalid construction produces
`InvalidArgumentException`.

`SEC-009` Token counting occurs before appending an over-limit token. Parser
recursion for prefix signs and right-associative powers reserves one
prospective AST level before descending and fails at the operator that cannot
fit. Grouping and calls reserve their node level at the opening delimiter and
are also guarded by the nesting limit. Iterative additive and multiplicative
construction checks the resulting depth at each operator. Evaluation never
begins for an over-depth AST.

## 9. Required implementation properties

`IMP-001` Build in this dependency order:

1. source span, token enum/value, lexer, and lexical exceptions;
2. immutable typed nodes for number, constant, variable, grouping, unary
   operation, binary operation, factorial, and function call;
3. recursive-descent parser and parse exceptions;
4. numeric operations, isolated environment, and evaluator;
5. immutable function definitions/registry, constants, and built-ins;
6. immutable options/limits and the public facade.

`IMP-002` AST nodes are final immutable value objects with typed properties.
They contain no evaluator callbacks or mutable environment references.
A grouping node spans both parentheses, has depth one greater than its child,
and evaluates to its child's value. Operation nodes retain both their complete
node span and the operator-token span needed by `ERR-004`.

`IMP-003` The parser and evaluator are instance-scoped. The facade creates a
complete per-call execution graph and returns only `int|float`.

`API-001` The public facade is `MathPHP\Math` and its operation is:

```php
Math::evaluate(
    string $expression,
    array $variables = [],
    ?EvaluationOptions $options = null,
): int|float
```

`EvaluationOptions` contains immutable `ResourceLimits` and an immutable
`FunctionRegistry`. The facade constructs a fresh lexer, parser, environment,
numeric evaluator, and evaluator for every call.

## 10. Test and documentation traceability

Every requirement must be covered directly or reviewed explicitly as a
non-testable release/documentation gate.

| Requirement IDs | Required evidence |
|---|---|
| `LANG-001..003`, `LEX-001..009` | lexer unit tests for every number form, identifiers, whitespace, malformed numbers, unknown/non-ASCII bytes, EOF, spans, and types |
| `SYN-001..005` | parser/AST tests for all precedence examples, left/right associativity, calls, commas, grouping, empty/trailing input, and deferred syntax rejection |
| `ENV-001..005` | evaluator/facade tests for types, constants, validation, unknown variables, and sequential/interleaved variable and function isolation |
| `NUM-001..010` | exact type tests, every operator, integer boundaries, signed zero, overflow, underflow, powers, factorial boundaries, NaN/Infinity rejection, and tolerance helper tests |
| `FUN-001..003` | one success and every arity/domain boundary for each built-in; unknown and case-mismatched functions; registry immutability; custom callback return/error/isolation tests |
| `ERR-001..005` | phase subclass, stable code, message position, exact spans, failure precedence, and evaluation-order assertions |
| `SEC-001..009` | exact-limit success and one-over-limit failure for each safeguard, including long unary/power chains |
| `IMP-001..003`, `API-001` | architecture review, strict static analysis, facade tests, and absence searches for mutable statics, `eval`, and dynamic-name dispatch |
| `DEF-001` | rejection tests for each tempting deferred syntax plus README limitations |
| `DOC-001` | every expression and result published in README or contract is executed by a documentation-example test |
| `PROP-001` | fixed-seed independently calculated bounded generated cases, with the seed printed on failure |
| `FUZZ-001` | deterministic malformed corpus and generated guaranteed-invalid inputs with bounded termination |
| `QUAL-001..003` | recorded successful quality commands, version matrix, and locked dependency audit |
| `REL-001..003` | manifest/config review, local and remote compatibility evidence, identity decision, final traceability audit, and release approval |

### 10.1 Bounded property tests

`PROP-001` Deterministic randomized tests use fixed recorded seeds and bounded
case count/depth. The generator independently builds both an expression and
its expected value from a generated structure. Initial properties use small
integers and `+`, `-`, and `*`, rejecting generated cases that would overflow.
The production lexer, parser, AST, or evaluator must not calculate the oracle.

At minimum, generated tests cover redundant grouping, whitespace insertion,
and precedence-preserving serialization. Failures print the seed and
expression.

### 10.2 Malformed-input fuzz tests

`FUZZ-001` A deterministic corpus covers malformed numbers, delimiters,
operators, commas, identifiers, non-ASCII bytes, NUL bytes, and every limit.
Additional bounded generated cases contain a guaranteed-invalid construct
rather than assuming arbitrary random bytes are invalid. Each case must
terminate within the test budget and produce only a documented expression
exception; expected results are not derived from the implementation.

### 10.3 Documentation examples

`DOC-001` Required grammar examples in `SYN-002` are public examples and must
execute as tests. Every later README API example must be represented verbatim
in the documentation-example test.

### 10.4 Quality checks

`QUAL-001` The local CI-equivalent aggregate must fail on any failure and cover:

- `composer validate --strict`;
- optimized Composer autoload generation with `--strict-psr` and
  `--strict-ambiguous`;
- PHP syntax lint for every project PHP file;
- PHPUnit with empty suites treated as failure;
- PHPStan at `level: max` against the PHP 8.2 minimum; and
- a PSR-12 check.

`QUAL-002` `QUAL-001`, the platform-requirement check, autoload smoke test, and
full PHPUnit suite must pass under every locally installed supported PHP
family. Static analysis and style may run once at the minimum version.
Supported but unavailable families require remote CI evidence before release.

`QUAL-003` A network-enabled `composer audit --locked` must report no known
dependency advisories before release. It is distinct from the reproducible
offline checks because advisory data is time-sensitive.

## 11. Compatibility and release gates

`REL-001` The supported runtime is PHP `^8.2`, without runtime dependencies
unless a later technical decision documents and justifies one.

`REL-002` Local verification must cover each installed supported PHP family.
At the time this contract was written, PHP 8.2, 8.4, and 8.5 were available;
PHP 8.3 was unavailable locally and requires remote CI coverage.

`REL-003` No v0.1 release is permitted until:

- the public identity decision is recorded;
- the final API and PHP compatibility range are reviewed;
- `composer test` and every `QUAL-001` check pass;
- all public examples execute in tests;
- every contract row has direct evidence;
- deferred features are documented truthfully; and
- no publish, tag, push, or repository initialization occurs without the
  separately required approval.
